# Adversarial Verification Loop Skill (双対的・対立的エージェント検証スキル)

このスキルは、コード実装やアーキテクチャ変更を行う際に、2つの対立するサブエージェントを自律駆動させ、妥協のない反復検証ループ（Adversarial Verification Loop）を回すことで、本番環境での不具合を極限までゼロに近づけるプロトコルです。

---

## 1. エージェントの役割分担

```
┌─────────────────────────────────────────────────────────────┐
│ 1. メインエージェント (親エージェント)                           │
│    - コード実装、リファクタリング、ビルド、進行統括              │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. ファクトチェックサブエージェント (fact_checker)               │
│    - 仕様準拠、コード整合性、アーキテクチャの妥当性を評価       │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. 検証サブエージェント (verification_critic / Devil's Advocate)│
│    - ファクトチェック結果を疑い、実機環境の物理的制約・        │
│      OS依存・UAC・ゾンビプロセス・エッジケースを徹底的に追及  │
└──────────────────────────────┬──────────────────────────────┘
```

## 2. 実行サイクル（再帰的検証ループ手順）

### ステップ 1: ファクトチェック
1. メインエージェントがコードを実装後、`fact_checker` サブエージェントへ修正内容を送信。
2. `fact_checker` がコードの整合性・API仕様・アーキテクチャの妥当性をチェック。

### ステップ 2: 検証・反論（Devil's Advocate）
1. `fact_checker` の評価レポートを `verification_critic` サブエージェントへ引き渡す。
2. `verification_critic` は無批判に承認せず、以下の観点から徹底的に反論・穴を突く：
   - Windows/OS実機における物理制約（DLL欠如、パススペース、UAC、環境変数汚染）
   - プロセスライフサイクル（親プロセス強制終了時のゾンビ化、ハングアップ時のタイムアウト）
   - ネットワーク・通信（動的ポート、CORS正規表現、プロトコル競合）
   - レースコンディション（非同期イベントの到達遅延、IPCハンドシェイク）

### ステップ 3: 判定とループ
- **反論・課題が提示された場合**:
  - メインエージェントが課題に対する解決策を実装。
  - 過去のファクトチェック結果と新たな課題を添えて **ステップ 1 へ再帰**。

## 4. 再発防止・強制ガバナンス条項 (Deterministic Rules of Engagement)

AIアシスタント（メインエージェント）は、以下のルールに**物理的・絶対的に拘束**されます：

1. **【並列送信の完全禁止】**:
   `fact_checker` と `verification_critic` に同時に同一メッセージを送ることは厳禁。必ず `fact_checker` のレポート本文をコピーして `verification_critic` に渡す直列パイプラインを順守すること。

2. **【途中終了・ユーザー丸投げの完全禁止】**:
   `verification_critic` から反論（REJECTED）や懸念点が出ている状態で、ユーザーへ返答を返して作業を中断することは**プロトコル違反**である。反論が出た場合は、必ずその場でコードを修正し、`fact_checker` ➔ `verification_critic` の再検証ループを自律的に回し続けること。

3. **【物理的ファクトチェックの義務化】**:
   「コードを書いた」「ビルドが通った」だけで承認してはならない。必ず `scripts/verify_build_integrity.ps1` や 7-Zip によるバイナリ解凍、実際のプロセス起動ログによる**物理的証拠（動かぬ証拠）**を取得して検証すること。

4. **【完了宣言の条件】**:
   ユーザーへ報告を行ってよい唯一の条件は、`verification_critic` が明示的に **`[RESULT: CLEARED] (完全承認)`** を宣言した場合のみとする。
